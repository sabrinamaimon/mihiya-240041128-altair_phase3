The Stop That Did Not Stick

Technical explanation & system design

1. Why the stop command didn't keep the rover stopped

In ROS 2, topics are stateless broadcast channels with no built-in priority. The motor subscriber simply executes whichever command arrived most recently.

Time (ms): 0 ms 40 ms 100 ms Nav (10 Hz): [Forward] ------------------> [Forward] (overwrites!) Obstacle node: [STOP (0,0)] Topic /cmd_vel: [Forward] ---> [STOP] ------> [Forward] Rover motion: Driving -----> Pauses ------> Driving again

Because the autonomous navigation node publishes forward commands continuously at 10 Hz (every 100 ms), a single zero-velocity message only takes effect until the very next timer tick. Approximately 60 ms later, the next forward command arrives on /cmd_vel and immediately resumes rover motion toward the obstacle.

2. Inspecting publishers with the ROS 2 CLI

To check which nodes are publishing to the command topic, we run:

$ ros2 topic info /cmd_vel --verbose Type: geometry_msgs/msg/Twist Publisher count: 2 Subscription count: 1 Endpoint 1: /autonomous_nav_node (Publisher) Endpoint 2: /obstacle_detector_node (Publisher)
  • What this output proves: It confirms that two separate nodes are currently registered as active publishers on /cmd_vel.
  • What we still need to observe: The endpoint list shows existence, but not timing. It does not tell us publication rates (10 Hz periodic vs a single event), message arrival order, or which node sent a given velocity vector. To observe those, we must use ros2 topic hz /cmd_vel and timestamped packet inspection with ros2 topic echo.

3. Safe command ownership & handling threshold flicker

To prevent competing messages, motion commands must have a single clear owner:

[ Navigation ] ------> /nav_cmd_vel (10 Hz) ---+ v [ Obstacle Node ] ---> /field_blocked ---------> [ Safety Supervisor ] ===> /cmd_vel ===> Motors ^ (Sole owner) [ Operator ] --------> /resume_mission --------+
  • Command ownership: The navigation node publishes to an internal topic (/nav_cmd_vel). A supervisor node is the sole owner allowed to publish to the hardware /cmd_vel.
  • Latched stop & explicit resume: When a hazard appears, the supervisor latches into a PAUSED state and continuously outputs zero velocity. Clearing the hazard clears the warning flag, but motion stays stopped until an operator explicitly calls /resume_mission.
  • Threshold flicker (Hysteresis): Near the detection threshold (e.g., 1.0 m), sensor noise causes readings to oscillate rapidly between 0.99 m and 1.01 m. We apply dual-threshold hysteresis: stop when distance is under 1.0 m, but only clear when distance exceeds 1.3 m (a 30 cm safety buffer), along with a 1-second debounce window.
